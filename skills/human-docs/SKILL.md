# 人类味项目文档

把「该写什么文档」「怎么写清楚」「怎么去 AI 味」「怎么验收」合在一条流程里。参考自 human-voice（形态→节奏→立场→用词）、deslop-zh / shuorenhua（中文去 AI 味）、Anthropic doc-coauthoring（读者测试），以及 documentation-criteria（文档路由）的思路；本 skill 自包含，不必再打开那些仓库。

## 何时用

用户要写、改写、润色、审稿、去 AI 味，或抱怨文档「像模型写的 / 不好懂」时启用。覆盖 PRD、设计文档、技术方案、ADR、RFC、README、API 文档、发行说明。

不要用于：纯翻译、只改错别字、从零发明事实来「装人」。

## 不变量（全程）

- 不改数字、日期、代码、命令、路径、URL、引用、专有名词
- 空句直接删，不拿编造细节填空；缺信息标 `[待补充]`
- 术语全文统一；中英混排：中文与英文/数字之间加空格（代码与 URL 除外）
- 技术文档默认不用第二人称「你 / 您」；直角引号「」；少用破折号与感叹号

---

## 步骤

### 1. 定文档类型与读者

先问清（或从上下文推断）三件事：

1. **类型**：PRD / 设计文档 / ADR / README / API / 发行说明 / 其它
2. **读者**：谁会用这份文档做决定或执行
3. **深度**：Quick（短消息级）/ Standard（内部文档）/ Full（对外或高风险）

粗路由（可按项目习惯调整）：

| 变更规模 | 通常需要 |
|---------|---------|
| 小修小补 | 可不写正式文档；changelog 一句即可 |
| 单功能 / 局部重构 | 短设计说明或 ADR |
| 跨模块 / 接口变更 | 设计文档 + 必要 ADR |
| 新产品 / 大需求 | PRD → 设计文档 → 任务拆分 |

只写读者真正需要的类型；不要为「看起来完整」凑章节。

### 2. 收集上下文，再动笔

动笔前凑齐：目标与非目标、约束、已定决策、待决问题、相关链接/代码路径。缺关键事实就问一轮短问题，不要猜。

写作顺序建议：

1. **先写结论 / 决策**（读者扫一眼就知道选了什么）
2. **再写理由与取舍**（为什么不选其它方案）
3. **再写机制与边界**（怎么做、不做什么、风险）
4. **最后写附录**（细节、备选方案、术语表）

禁止：开篇「随着…发展」「在当今…时代」；禁止用「几种方案各有优劣」结束而不表态。

### 3. 按类型落最小骨架

**PRD**：背景与问题 → 目标 / 非目标 → 用户与场景 → 需求（可验收）→ 成功指标 → 范围外 → 开放问题

**设计文档**：背景 → 目标与非目标 → 方案（含关键决策）→ 数据流 / 接口 → 失败与边界 → 迁移 / 回滚 → 测试要点 → 开放问题

**ADR**：状态 → 背景 → 决策 → 后果（正/负）

**README**：一句话是什么 → 快速开始 → 配置 → 常见问题；少用宣传形容词

**API 说明**：用途 → 鉴权 → 端点（方法、路径、参数、响应、错误）→ 示例；代码与字段名原样保留

章节只保留有内容的。空章节（「安全性」「可扩展性」却只有一句话套话）要么补实，要么删并标 `[待补充]`；不要为凑大纲灌水。

### 4. 去 AI 味（改写顺序固定）

按这个顺序改，**不要先从换词开始**：

1. **形态**：砍掉助手腔排版——过密标题、处处加粗、Key takeaways / 综上所述、均匀分段的「答题结构」
2. **结构**：合并重复章节；按读者问题分配篇幅；同一文档保持同一深度
3. **节奏**：句长要有起伏；避免整篇落在差不多长度的中句；段末总结句优先删
4. **实质**：删空话与复述；有判断就表态；信任读者，不 babysit
5. **用词**：最后才处理黑话与填充词

#### 中文高频检查

- 段末「这说明 / 可以看出 / 到这里 / 由此可见」→ 删
- 「不是…而是…」→ 改成直接陈述结论
- 黑话默认不用：赋能、抓手、闭环、沉淀、拉通、对齐、赛道、心智…
- 「值得注意的是 / 综上所述 / 一句话总结」→ 删标签，直接说内容
- 技术文档禁用「你 / 您」；不用感叹号与宣传词（领先、强大、颠覆）
- 假主体：「数据告诉我们」→ 改成真实主语或直接陈述

#### 英文高频检查（若混写）

少用 delve / leverage / seamless / robust / comprehensive；少堆 em-dash；少 rule-of-three 与 “not X, it’s Y”；少 chatbot 开场（Great question / Let’s dive in）。

#### 反过矫正

不要为了「像人」硬塞口语、碎句、lol、刻意全小写。自然准确优先于风格表演。

### 5. 轻量读者测试（Standard / Full）

定稿前做一次「冷读」：假设读者没参与讨论、只有这份文档。自问或另开无上下文检查：

1. 这份文档要解决什么问题？
2. 最终决策 / 推荐是什么？
3. 主要风险或限制是什么？
4. 下一步该谁做什么？
5. 有没有未定义术语或跳步？

答不上来或要靠「作者常识」才能懂 → 回改文档，不要只在聊天里解释。Full 深度可扩到 5–8 个针对性问题。

### 6. 交付

- 直接给出改写后的文档（或文件 diff），开头不要「好的，我已经…」
- 若用户需要，可附极短审计：删了什么腔、补了哪些 `[待补充]`、读者测试卡住的点
- 缺事实处保留标记，等作者填；不要发明指标或引用

---

## 质量自检（交付前扫一遍）

- [ ] 读者 30 秒内能抓住决策或用法
- [ ] 没有空章节灌水；没有段末总结腔与开篇套话
- [ ] 数字 / 代码 / 链接未改坏
- [ ] 中文黑话与「不是…而是…」已处理；术语一致
- [ ] 冷读问题能靠文档本身答出

## 深度对照

| 深度 | 做什么 |
|------|--------|
| Quick | 形态 + 删空话 + 用词快扫；不做完整读者测试 |
| Standard | 完整 1–6 步；读者测试 4–5 问 |
| Full | 加完整审计；读者测试更细；对外稿再扫一遍宣传腔与假平衡 |
